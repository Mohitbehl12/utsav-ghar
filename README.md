# 🎊 Utsav Ghar — every Indian festival, pooja, décor, crockery & kitchen

A complete e-commerce platform: customer storefront, admin panel and a secure API.

| Layer | Tech |
|---|---|
| Storefront + Admin | React 18, Vite 5, React Router, hand-written CSS (design tokens, light + dark) |
| API | Node 20+, Express 4, better-sqlite3 (WAL), Zod validation |
| Auth | bcrypt (12 rounds), JWT in httpOnly cookies, separate admin session, double-submit CSRF |
| Payments | UPI QR / UPI ID with admin verification **or** Razorpay with server-side signature + webhook verification |
| Shared | `shared/pricing.js` — the one promotion engine, used by the server (authoritative) |

## 1. Quick start (local)

```bash
npm run install:all            # installs server + client
cp server/.env.example server/.env   # set JWT_SECRET / ADMIN_JWT_SECRET (optional in dev)
npm run seed:demo              # catalogue, offers, admin user + 3 sample orders
npm run dev:server             # API on http://localhost:4000
npm run dev:client             # store on http://localhost:5173 (proxies /api)
```

* Store: http://localhost:5173
* Admin: http://localhost:5173/admin — `admin@utsavghar.in` / `ChangeMe@2026` (**change it** in Admin → Payment & Store → Your admin password, or set `ADMIN_EMAIL`/`ADMIN_PASSWORD` before the first seed)
* Tests: `npm test` (pricing engine unit tests) and `node server/test/e2e.mjs` against a running server (full order → payment → admin lifecycle, CSRF, tampering checks)

## 2. Production

```bash
npm run build          # client → client/dist (code-split, hashed, minified)
NODE_ENV=production npm start   # Express serves the API + the built site on one origin
```

Put Nginx / Caddy / a platform load balancer in front for TLS. The server trusts one proxy hop, redirects HTTP→HTTPS, sets `Secure` cookies and strict security headers (Helmet CSP).

**Recommended hosting:** any Node host with a persistent disk (Railway, Render, Fly.io, a VPS with PM2). Keep `server/data` and `server/uploads` on the persistent volume and back them up daily (`sqlite3 data/utsav-ghar.db ".backup backup.db"`). Serve `/assets` and `/uploads` through a CDN (Cloudflare) — both are sent with long-lived immutable cache headers.

**Scaling beyond one server:** the schema in `server/src/db.js` is written to port 1:1 to PostgreSQL (INTEGER PK → BIGSERIAL, TEXT JSON → JSONB). Swap `better-sqlite3` for `pg`, move uploads to S3/R2, and run multiple API instances.

## 3. How the Diwali offer works (and why it's safe)

The browser only ever sends `{ productId, qty }` and an optional coupon code. **Every price, discount, delivery fee and total is calculated on the server** by `computeQuote()` in `shared/pricing.js`:

```text
eligible_units = sum(qty of cart lines whose product is in offer.product_ids
                     OR whose category is in offer.category_ids)      -- both empty = whole store
Offer types:
  percent   – X% off eligible items once eligible_units >= min_qty
  flat      – ₹X off
  tiered    – Buy 2 → 10%, Buy 3 → 20%, Buy 5 → 30% (highest tier reached wins)   ← default Diwali offer
  cheapest  – for every group of min_qty eligible items, the cheapest one is X% off
Discount capped at max_discount. first_order_only coupons (e.g. WELCOME10) check phone + email history.
Best single offer wins — offers never stack. The discount is split across lines (discount_share)
so per-product profit stays exact.
delivery = shipping zone fee (+ extra-item fee abroad); free above the zone's threshold
```

Why not "Buy 3 get 50% off everything"? At normal costs it sells most products below cost (Admin → Profit shows this). It is still included as a switched-off offer for clearance.

Money is stored as integer **paise** everywhere. `POST /api/orders` recomputes the quote inside a DB transaction, reserves stock atomically (`UPDATE … WHERE stock >= qty`), and rejects the order with `409` if the total the customer saw (`expectedTotal`) no longer matches — so a changed price or expired offer is never silently charged.

Admins change offers in **Admin → Offers** (name, type — %, flat, tiers or cheapest-item — minimum quantity, eligible categories/products, dates, max discount, coupon code, on/off). Changes apply to every cart immediately.

## 4. Payment flow

1. Customer places the order → status **Order Placed**, payment **Awaiting Payment**, stock reserved.
2. Payment step shows a **UPI QR generated for the exact amount** (or the owner's uploaded QR), the UPI ID with **Copy UPI ID**, and **Pay using UPI app** (`upi://pay?...` deep link on phones).
3. Customer enters the **UTR** (and optionally a screenshot) and taps **I HAVE PAID** → **Payment Verification Pending**. A UTR can only be used once across all orders.
4. Admin → Payments → matches the UTR and amount against the bank / UPI merchant statement → **Confirm** (or **Reject**; the customer can resubmit).
5. Order moves **Payment Confirmed → Processing → Shipped (courier + tracking no.) → Out for Delivery → Delivered**. Cancelling restores stock; paid cancellations can be marked refunded.

> A UTR or screenshot entered by a customer is **not** proof of payment — it only queues the order for verification. Screenshots are stored outside the public web root and are streamed only to signed-in admins.

**Automatic verification (recommended at scale):** set `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` in `.env`, put the publishable key in Admin → Payment & Store, and switch mode to *Gateway*. Checkout then opens Razorpay (UPI intent/QR, cards, netbanking); the server verifies the HMAC signature (`/api/payments/gateway/verify`) and the webhook (`/api/payments/webhook/razorpay`, raw-body HMAC) before confirming. Point the Razorpay webhook at `https://your-domain/api/payments/webhook/razorpay` for events `payment.captured` and `order.paid`. Other providers (Cashfree, PhonePe PG, PayU) plug into `server/src/lib/razorpay.js`'s three functions.

## 5. Admin: products, photos, prices & profit

* **Admin login:** `/admin` (also linked as “🔐 Admin login” in the site footer and the mobile menu).
* **Add a product:** Admin → Products → *Add product*. Drag photos in (or tap to pick from your phone gallery), fill name, category, description, **Original price (MRP)**, **Selling price** and **Your cost**. A live calculator shows profit per unit, margin, the customer's saving, and whether the product still makes money at the Buy-3 offer price. Photos upload when you press *Create product*; the first photo is the main image.
* **Cost is private:** `products.cost_price` is only returned by admin endpoints. Each order line stores the cost at the time of sale (`order_items.unit_cost`) and its share of the order discount (`order_items.discount_share`), so profit reports stay correct after you change prices.
* **Profit & pricing page** (Admin → Profit & pricing):
  - Tiles: revenue after discounts, cost of goods sold, gross profit and margin, stock value at cost.
  - Chart: one bar per product, full length = MRP, split into *your cost* | *profit* | *discount off MRP*; a hatched segment marks selling below cost, and a dashed tick marks the effective price under the Buy-3 offer (red when that price is below cost). Hover a row for exact numbers.
  - Editable table: change MRP / selling / cost inline and press Enter; the store updates immediately.
  - A warning lists products that lose money when the 50% offer applies, so you can raise prices or remove them from the offer.

### Product photos (Admin → Product photos)

* Drop any number of photos at once. Files named after the product's URL slug (`premium-brass-diya.jpg`, `premium-brass-diya-2.jpg`) are matched automatically; other names get a best guess you can correct from a dropdown.
* Photos are resized to max 1600 px and converted to WebP in the browser before upload (a 6 MB phone photo usually becomes ~200–400 KB), with EXIF rotation fixed.
* *Replace existing photos* swaps a product's photos; otherwise new ones are added after the current ones. The first photo is the main image.
* The **Photo checklist** lists products without photos, the file name to use, and search links to Pexels / Unsplash / Pixabay (free for commercial use; check each photo's licence page). Don't reuse photos from other sellers' listings or marketplaces.

## 6c-3. Search ranking, Best Sellers Rank & "Customers who bought this also bought"

`shared/ranking.js` implements the methods Amazon has published (its production models are private):

- **Item-to-item collaborative filtering** (Linden, Smith & York 2003; improved scoring from Smith & Linden 2017). For every pair of products it compares how many *customers* bought both with how many would by chance, `(observed − expected) / √expected`, so popular items and bulk buyers don't dominate. Powers "Customers who bought this item also bought" and feeds Frequently bought together, Recommended for you and cart suggestions.
- **Two-stage search**: (1) text relevance with field weights (title > category > specs > description), Hinglish synonyms (diya/deepak, thali/plate, pital/brass, kadhai/kadai, crockery/crockari…), plurals and typo tolerance; (2) re-ranking by behaviour: sales velocity (7-day half-life), conversion rate (views → orders, with a prior), Bayesian-averaged rating, review volume and stock. Behaviour can lift an item at most ~35%, so better text matches still win. "Showing results for …" spelling correction, and unmatched words are dropped when nothing matches.
- **Sort by** Featured, Price, Avg. Customer Review, Newest Arrivals, Best Sellers, Discount.
- **Best Sellers Rank** per category from recent sales ("#1 Best Seller" badge, "Best Sellers Rank #2 in Diyas & Candles" on the product page). Before the first sales it uses your Bestseller flag and review counts.
- **Utsav's Choice**: one pick per category that is well rated (Bayesian ≥ 4.2, 20+ reviews), priced at or below ~1.25× the category median, in stock and selling well.
- **"50+ bought in past month"**: shown only from real orders (10+).

History is recomputed every 5 minutes; product edits show immediately. The demo preview uses simulated shopper history so these features have data to show.

## 6c-6. Security

No website can honestly be called "unhackable" — but this one is built so that common attacks fail, mistakes are limited, and you can recover. `npm run e2e:security` attacks a running server with 54 checks (SQL injection, XSS, CSRF, forged logins, brute force, order snooping, price tampering, path traversal, oversized requests, bots, 2FA bypass…) — all must pass.

**Admin panel**
- First sign-in **forces a new password** (the setup password is public in this guide); nothing else works until it is changed. Admin passwords: 10+ characters, letters + number, not common, not your name/email.
- **Two-step login** with an authenticator app (Google/Microsoft Authenticator, Authy): Admin → 🛡️ Security. 10 single-use backup codes. A code can't be reused.
- **Lockout**: 5 wrong passwords or codes → that account is locked 15 min (then 1 h, then 24 h), plus per-IP limits on failed sign-ins.
- **Sign out everywhere**; changing the password ends every other session. Admin sessions last 12 h, in a separate `SameSite=Strict` cookie with its own secret.
- Roles: only owner/manager can confirm or reject payments; only the owner can mark refunds, change payment settings or export customers. Everything is in the Audit log.
- Optional: `ADMIN_ALLOWED_IPS` limits the admin panel to your own internet connection(s).
- Admin → Security shows a checklist, recent sign-ins, failed/blocked attempts and locked accounts.

**Customers**
- Passwords hashed with bcrypt (cost 12); weak/common passwords refused; strength meter.
- Lockout after 5 wrong passwords; sign-in timing doesn't reveal which emails exist.
- Account → Login & Security: change password (signs out other devices + email alert), sign out everywhere, recent activity, **download my data**, **delete my account** (DPDP Act 2023). Orders are kept without the account because GST law requires invoices.
- Guests see their own order only with a secret per-order token; order numbers alone reveal nothing.

**Payments**
- Prices, discounts and totals are always calculated on the server; anything the browser sends about price is ignored.
- Razorpay: checkout signature and webhook signature (HMAC-SHA256 over the raw body) verified; amounts checked; secrets only in `.env`.
- UPI: each UPI reference (UTR) can be used once; screenshots stored privately (admin-only), images verified by file signature.

**Website**
- HTTPS redirect, HSTS (1 year, preload-ready), strict Content-Security-Policy (no inline scripts, no framing — stops clickjacking), `X-Frame-Options: DENY`, `nosniff`, strict referrer, Permissions-Policy (microphone only for voice shopping, camera/location off).
- CSRF tokens on every change; cookies `HttpOnly`, `Secure`, `SameSite`.
- All database queries use parameters (no SQL injection); all input validated (zod); request size limits; rate limits.
- Hidden "honeypot" fields block simple bots on sign-up, contact and newsletter forms.
- Dependencies audited: `npm run audit:deps` (0 known vulnerabilities at release; nodemailer and react-router were upgraded).
- `/.well-known/security.txt` tells researchers how to report issues.

**Backups & recovery**: the database is backed up daily (keeps 14) into `server/backups/`; `npm run backup` makes one now. Copy backups off the server (e.g. rclone → Google Drive/S3). Restore = stop server, copy a backup over `DB_PATH`, start.

**"Can someone copy my code?"** Anything a browser runs (the shop's look and screens) can always be viewed — that's true for every website, including Amazon. It is minified and has no source maps, and it contains **no secrets**. Your server code, database, payment keys and passwords stay on your server and are never sent to browsers.

**Server checklist when you go live**
1. `NODE_ENV=production`, long random `JWT_SECRET` and `ADMIN_JWT_SECRET` (the server refuses to start without them).
2. Put it behind Cloudflare (free plan): DDoS protection, WAF, "Always use HTTPS", bot fight mode.
3. Server: SSH keys only (no password login), firewall open for 80/443 only, automatic security updates, run Node as a normal user (not root), `.env` readable only by that user (`chmod 600`).
4. Turn on two-step login for every admin; give staff the `support` role.
5. Keep dependencies updated monthly: `npm run audit:deps`.
6. Check Admin → Security weekly.

## 6c-7. Cards, net banking, EMI · Chat assistant · Help Center

**All payment types.** The payment step offers UPI, Credit/Debit cards (Visa, Mastercard, RuPay, American Express, Diners, Maestro — including international cards), Net Banking, Wallets and EMI / Pay Later. Everything except UPI QR opens the payment gateway's own window (Razorpay by default), so:
- card numbers are typed **only** in the gateway's PCI-DSS certified window and never reach your server — you don't need PCI certification yourself;
- the bank confirms with OTP / 3-D Secure, and the server verifies the gateway's signature before marking the order paid;
- only "Visa credit •••• 4242"-style details are saved, shown in Admin → Payments.

## 6c-9. How many shoppers at once?

Measured on a 2-vCPU machine (production mode, load tool on the same machine):

| Endpoint | Requests / second |
|---|---|
| Product list / search | ~1,500–2,000 |
| Search suggestions | ~2,000 |
| Product details | ~1,700 |
| Recommendations | ~1,900 |
| Server-rendered product page | ~1,100 |

A shopper browsing makes roughly one request every 2–3 seconds, so one 2-vCPU server handles about **2,000–3,000 shoppers at the same moment**. There is no limit on how many customers can be signed in (sign-in uses stateless tokens).

What makes this fast: a 3-second catalogue snapshot (refreshed instantly after any admin edit, order or payment), cached product text for search, and a small response cache for the busiest pages. Checkout always re-reads live price and stock.

Bigger festival traffic: put Cloudflare (free) in front for images/JS, move to a 4-vCPU server (roughly doubles capacity), and later switch SQLite → PostgreSQL to run several servers.

## 6c-10. Dealer order management (dealer app)

Orders flow **website → store → dealer → customer**. Dealers never take orders from customers directly.

**Flow (customer sees every step):** Order Received → Payment Confirmed → Sent to Dealer → Order Accepted → Packed → Ready for Delivery → Out for Delivery → Delivered

- **Routing (automatic):** when payment is confirmed, the whole order goes to ONE dealer who sells every item in it (by category or product) and delivers to the customer's PIN code. Nearest shop and higher priority win. Rules: `shared/dealers.js`.
- **Dealer app:** `https://your-store.in/dealer`. It is a phone-first web app; dealers can add it to the home screen. Dealers sign in with their mobile number + a one-time password and must set their own password. There is a sound/vibration alert and a WhatsApp/SMS/email message for each new order.
  - **Before accepting:** the dealer sees products, quantity and the city/PIN only.
  - **After accepting:** the customer's name, phone and address are shown.
  - **Never shown:** payment details or the customer's email.
  - **Packing:** the dealer ticks every item and can print a packing slip.
- **Delivery:**
  - **Own delivery person:** the dealer enters their name and mobile number. The customer gets a 4-digit code on the order page and by message, and the order is marked Delivered only with that code.
  - **Courier:** the dealer enters the courier company, AWB number and tracking link.
- **If a dealer rejects or doesn't accept in time:** a reminder goes out at half time, then the order moves to the next dealer automatically (Admin → Dealers → Routing). The admin can also move an order by hand from the order screen.
- **Admin → 🏪 Dealers:**
  - order board (in progress / late / every status, plus paid orders without a dealer)
  - dealer accounts (PIN codes as `110017`, `1100` or `400001-400099`; categories; priority; on/off)
  - stats (open, waiting, delivered, minutes to accept, declined)
  - password reset (signs the dealer out everywhere)
- **Cancelled by the store:** the dealer is told not to ship, and the app blocks further steps.

API: `/api/dealer/login|logout|me|summary|orders|orders/:number/(accept|reject|pack|ready|dispatch|deliver)`, admin `/api/admin/dealers`, `/api/admin/dealer-orders`, `/api/admin/orders/:id/dealer`, `/api/admin/dealers-settings`. Tests: `server/test/dealers.test.js`, `server/test/e2e-dealer.mjs`.

## 6c-12. Dealer product submissions & pricing (strict role separation)

**Flow:** Dealer adds product + their price → email to your team → Admin review → Expenses + profit calculation → Customer price → Published

- **Dealer app → 🛍️ My products → ＋ Add a product.** The dealer enters:
  - photos (1–6; kept private until the product is approved)
  - name, category, description
  - details: material, size, weight, what's included, colour, care, origin
  - **their price per piece** and the quantity available
  - SKU and HSN (optional)

  After sending, the dealer sees the status: Under review / Changes needed (with your note) / Approved & Live / Not accepted. They can edit and re-send, and update availability, which changes store stock at once.
- **Email to your team** for every new or updated product, with all the details and a review link. Set the email in Admin → 🧾 Dealer products → ⚙️ Default costs. If it isn't set, it goes to the store support email.
- **Admin → 🧾 Dealer products** has the review queue and the review screen:
  - **Listing:** photos and fully editable listing text.
  - **Price calculator:** dealer price + shipping + packaging + other expenses + profit (fixed ₹ or % of the dealer price), divided by (1 − platform/payment fee %), plus GST %, then rounded (exact, ₹…9, or ₹…49/₹…99). It shows profit per piece, margin % and markup %. You can override the final price and add an MRP.
  - **Safety check:** publishing below the dealer price is blocked unless you tick "sell below cost".
  - **Actions:** Approve & publish, Approve but keep hidden, Ask for changes, or Reject. The dealer gets a WhatsApp/email message, which never includes prices.
  - Example: ₹400 + ₹100 expenses + ₹300 profit = **₹800**.
- **Who sees what:**

| | Dealer | Customer | Admin |
|---|---|---|---|
| Dealer price (₹400) | ✅ own products only | ❌ | ✅ |
| Expenses, profit, margin, calculation | ❌ | ❌ | ✅ |
| Customer price (₹800) | ❌ not in the dealer app | ✅ | ✅ |

  Every dealer response is built from a whitelist of fields, and automated tests check that no price, MRP, margin, profit or internal note is ever sent to a dealer. Publishing sets the product's cost to the dealer price and links the product to that dealer, so customer orders for it go straight to them.
- **One limit:** the customer price is shown on the public website, so a dealer who visits the store like any shopper can see it there. The dealer app and the dealer's messages never show it.

API: dealer `/api/dealer/products` (GET/POST/PUT/DELETE, `PATCH /:id/stock`), admin `/api/admin/dealer-products` (+ `/:id/publish`, `/:id/request-changes`, `/:id/reject`), `/api/admin/dealer-products-defaults`, `/api/admin/dealer-products-calc`. Tests: `server/test/e2e-dealer-products.mjs`.

## 6c-13. Pricing by PIN code (delivery charge, courier cost, profit per zone)

The **product price is the same everywhere**. Two things change by the customer's PIN code:

1. **Delivery charge the customer pays.** You set it per zone in Admin → 🧮 Pricing by PIN → Delivery charges, along with the order value above which delivery is free. Cart and checkout recalculate it as soon as the customer types their PIN.
2. **Courier cost you pay.** It is a **live Shiprocket rate** when `SHIPROCKET_EMAIL` / `SHIPROCKET_PASSWORD` are set (cached 24 h per route and weight). Otherwise it comes from your **rate card** (first 0.5 kg + each extra 0.5 kg per zone, plus fuel %).

**Zones** run from the dealer's shop (or your pickup PIN) to the customer:

| Zone | Means |
|---|---|
| Local | same city (first 3 PIN digits) |
| Regional | same state |
| Metro to metro | Delhi, Mumbai, Kolkata, Chennai, Bengaluru, Hyderabad, Pune, Ahmedabad |
| Rest of India | everywhere else |
| Special areas | North-East, J&K, Ladakh, Andaman, Lakshadweep |

**Chargeable weight** is the higher of the packed weight (+10 %) and the box volume (L × W × H ÷ 5000, with 2 cm packing on each side), rounded up to 0.5 kg. Weight and box size come from the product details, or set them in the calculator ("Save weight & box size").

**Profit for one order:**

```
Customer pays      = product price + delivery charge (0 above the free-delivery amount)
− GST              = customer pays × GST% ÷ (100 + GST%)      (only if your prices include GST)
− Platform fee     = customer pays × fee %                    (Razorpay etc.)
− Product cost     = dealer price / cost price
− Packaging, other expenses
− Courier          = Shiprocket live / rate card / your actual courier bill
= Profit           (margin % = profit ÷ price without GST)
```

**Admin → 🧮 Pricing by PIN** has three tabs:

- **Calculator:** pick any product or type custom numbers. You see profit for every zone and up to 10 PIN codes. Type your own courier number in any row to override it, and click a row for the full line-by-line calculation. Enter "profit you want" to get a suggested price per zone, then press **Use** to set it.
- **All products:** profit per zone for every product (1 piece). It flags products that lose money somewhere, have no cost price or have an unknown weight. Includes CSV export.
- **Delivery charges & courier rates:** the zone table, pickup PIN, fuel % and the Shiprocket connection status.

**Every order** records its zone, origin PIN, chargeable weight and courier estimate. In the order screen you can type the **actual courier bill**, and the order's profit updates.

API: `/api/admin/pricing/settings`, `/products`, `/calc`, `/export.csv`, `/products/:id/parcel`, `/orders/:id/courier-cost`. Cart quote accepts `pincode`. Tests: `server/test/shipping.test.js`, `server/test/e2e-pricing.mjs`.

## 6c-18. Sign-up codes, password reset, cancellations, returns, refunds, settlements, admin roles

**Sign-up & passwords**
- New customers confirm a 6-digit code (`POST /api/auth/register/otp`, then `POST /api/auth/register` with `otp`). Turn it off with `SIGNUP_OTP=0` (on by default).
- Codes: HMAC-hashed in `otp_codes`, valid 10 minutes, 5 tries, resend after 30 s, max 5 per hour per number. The copy saved in `notifications` is masked (`••••••`). Outside production the API also returns `dev_otp` so you can test without SMS — **never** in production.
- Forgot password: `/forgot-password` (customer), `/dealer/forgot` (dealer). The answer is the same whether or not the account exists. A reset signs out every other device.
- A customer can change their email (code sent to the new address) and edit / delete addresses; mobile numbers are unique.

**Cancellations, returns, refunds** (`server/src/lib/returns.js`, `shared/returns.js`)
- The customer can cancel until the dealer packs the order; stock goes back and, if paid, a full refund opens.
- Returns: within 7 days of delivery (48 h for damaged / wrong / missing — photo required). Admin → Returns & refunds: approve (refund can only be lowered) or reject with a reason → mark received (restocks) → refund opens.
- Refunds are recorded with a unique reference. Total refunds can never exceed what was paid; one cancellation refund per order. A gateway payment that arrives after cancellation opens a refund automatically.

**Dealer settlements** (`server/src/lib/settlements.js`, `shared/settlement.js`)
- Admin → Dealer settlements: preview what is due (delivered orders − returns, at dealer price; commission model: − commission % − per-order fee − payment fee %), create a batch, mark paid with a unique UTR. An order or return can be in only one active batch; a batch is never created for ₹0 or less.
- Dealer app → Payments shows the next settlement and paid batches — dealer price only (`assertDealerSafe`).

## 7. Security checklist (implemented)

- HTTPS redirect + HSTS + CSP (Helmet); `x-powered-by` off
- Passwords: bcrypt 12 rounds; constant-time login (dummy hash for unknown emails)
- Customer and admin sessions are separate httpOnly cookies with separate secrets; admin cookie `SameSite=Strict`, 12 h
- CSRF: double-submit token on every state-changing request (webhooks excluded, they're HMAC-signed)
- Rate limits: 300 req/min/IP overall, 10 sign-ins/15 min, 30 order writes/10 min, 20 tracking lookups/10 min
- Zod validation on every input; parameterised SQL only; `LIKE` wildcards escaped
- React escapes all output; JSON-LD is `<`-escaped; uploads verified by magic bytes, 5 MB cap, random filenames
- Guest orders are readable only with a per-order secret token (stored hashed) or the owning account; public tracking requires order ID **and** phone and hides PII
- Payment secrets only in environment variables — never in the DB, API responses or frontend
- Admin roles (`owner`, `manager`, `support`); settings changes are owner-only; every admin action is written to `audit_logs`

## 8. SEO & performance

- Server injects per-URL `<title>`, meta description, canonical, Open Graph and **Product JSON-LD** (price, availability, rating) into the HTML — crawlers and WhatsApp previews see real data without JavaScript
- Clean URLs: `/shop/<category>/<product>`; `sitemap.xml` and `robots.txt` generated from the catalogue
- Route-level code splitting (checkout, account, admin load on demand), hashed assets cached for a year, gzip compression, lazy-loaded images, fonts with `display=swap`
- Admin uploads accept WebP/AVIF; serve them via CDN for responsive sizing
- Festive canvas animation pauses off-screen and respects `prefers-reduced-motion` plus an on-site "Reduce animations" toggle

## 10. Before going live

1. Set real `JWT_SECRET`, `ADMIN_JWT_SECRET`, `PUBLIC_URL`; change the admin password.
2. Admin → Payment & Store: your **UPI ID**, payee name, merchant details, delivery fee and free-delivery threshold. Optionally upload your QR (leaving it empty gives customers an amount-prefilled QR).
3. Admin → Products: upload real photos (they replace the built-in illustrations), confirm prices and stock, and enter your real **cost** for each product (the seeded costs are examples).
4. Review the policy pages (`client/src/pages/Info.jsx`) with your own terms, GST details and return rules.
5. Configure SMTP / WhatsApp in `.env` for order notifications (unconfigured channels are logged as *skipped* in the `notifications` table).
6. Point a daily backup at `server/data/` and `server/uploads/`.
7. Run with `NODE_ENV=production` behind HTTPS (turns on Secure cookies and HSTS, and hides test codes). Set `COURIER_WEBHOOK_SECRET` and, if used, Razorpay keys — then test one real payment and one refund in Razorpay test mode.
8. Admin → Admin users & roles: give each person their own login with the smallest role they need, and turn on 2FA for every owner.
9. Have a qualified lawyer review every legal text in Admin → Legal & Compliance before publishing; the drafts are not legal advice.
